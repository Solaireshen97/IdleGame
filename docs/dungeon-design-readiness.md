# 副本设计接入说明

这份说明供下一轮具体副本、战斗机制与数值设计使用，整理配置入口、房间规则快照和挑战生命周期边界。2026-10-01 已接入火深层 LV2 的单次核心、LV3 的单次核心与扩散联动，以及 LV4 的周期循环，使用各层独立数值，见 [LV2 参数与验证](t1-fire-deep-lv2-balance.json)、[LV3 参数与验证](t1-fire-deep-lv3-balance.json)、[LV3 模拟记录](t1-fire-deep-lv3-simulation.json) 和 [LV4 参数与验证](t1-fire-deep-lv4-balance.json)；其他属性深层 Boss 仍需分别设计。

## 当前可使用的能力

- 房间内支持多波怪物，每波可以配置多个怪物；战斗按波次、位置依次处理，同一时刻只有一名活动敌人。
- 怪物支持基础属性、属性类型、技能编成、意图、打断、冷却、血量和回合条件、状态应用。火深层另有 `FireCore` 阶段配置：LV2、LV3 使用 `TriggerHpPercent=65`，首次达到血量条件后的下一次完整玩家回合开始触发，只出现一次；LV3 增加随机扩散，LV4 改为 Boss 局部回合循环。三者都支持累计实际水伤破核和后续完整回合奖励，阶段状态在 `BattleMonsterPhaseStates` 中随战斗回合持久化。
- 深层挑战支持层数成长、前置通关、最高层记录、精通收益和挑战碎片。角色在某次挑战中的精通等级会单独记录，通关提高的精通收益从后续挑战生效。
- 支持组队血量倍率、击杀奖励、通关奖励、首次通关奖励、失败结算、手动重置和自动重复挑战。
- 房间状态、回合状态、技能和消耗品冷却、怪物意图、奖励事件、参与记录各有明确存储；战斗计算由调用方一次保存，房间版本承担并发冲突检测。

多波不等于多敌同时战斗；配置 `IsBoss` 可以标识怪物并参与既有深层技能编成选择。火核心已支持前排攻击联动另外两名随机存活角色；任意 Boss 阶段、召唤物和其他选敌方式仍需对应执行器支持。

## 配置入口与层级

世界目录 `World` 位于 [Game.Server/world.json](../Game.Server/world.json)，其他默认配置节位于 [Game.Server/appsettings.json](../Game.Server/appsettings.json)，配置类型位于 [Game.Server/Configuration](../Game.Server/Configuration)。新副本先保持稳定的副本、技能、状态、奖励表代码，再设计数值。

| 配置节 | 负责内容 | 设计注意点 |
| --- | --- | --- |
| `World` | 区域、副本身份、开放条件及基础目录 | 副本代码用于关联编成、奖励与进度，不应把展示名称当标识 |
| `DungeonEncounters.Dungeons` | 波次、位置、怪物基础属性、战斗与奖励编成代码、`IsBoss`、`DepthStats` | 列表顺序决定串行出场顺序；`DepthStats` 可为指定层单独设置生命和攻击，后续从最近的独立面板继续增长 |
| `DungeonEncounters.RewardEligibility` | 某副本的奖励资格策略 | 可显式覆盖默认策略，不再用“是否深层”隐式决定全部奖励资格 |
| `MonsterCombat` | 怪物技能、技能编成、状态定义、深层编成变化 | 引用的技能和状态必须存在；新增效果类型仍需执行器支持 |
| `CombatDamage` | 双方直接伤害的小幅随机波动 | `VariancePercent` 当前为 3；参数随房间冻结，技能描述仍表示基础倍率 |
| `PartyScaling.Profiles` | 1～5 人怪物血量百分比 | 开战后人数减少不会降低本次已达到的倍率；增加成员可提高倍率 |
| `DungeonDepths.Dungeons` | 层数成长、最大层数、前置、精通与挑战收益 | 血量和攻击按现有公式向上取整；应先检查最高层整数溢出 |
| `Rewards` | 击杀、通关和首次通关的基础奖励表、组队掉率参数 | 怪物可使用独立击杀表，通关使用副本对应表；`CoopDropBonus` 按实际参战账号增加基础随机道具掉率 |
| `Planting` | 稀有种子代码、来源与掉落概率 | 房间冻结副本相关的种子概率；种子的使用与种植遵循全局规则 |

数值设计时应区分四个层级：角色等级决定玩家已有成长；副本深层 `DepthLevel` 决定这间房的挑战层数；深层定义 `Stage` 表示配置中的阶段标识；角色副本精通由既有最高通关层数计算，目前封顶 LV4。不要将这些字段都解释为怪物等级。

`DungeonDepths.Dungeons.<副本代码>.UsesPlaceholderBalance` 默认 `true`。部分层数完成验证时，可通过 `CalibratedDepths` 仅移除这些层的占位提示；火深层当前为 `[1, 2, 3, 4]`。整个副本完成校准后才将 `UsesPlaceholderBalance` 设为 `false`。这些标记只声明设计状态，不会更改成长公式或结算数值。火 LV3 已替换旧占位面板与技能；五波生命、攻击均严格按 LV1<LV2<LV3<LV4 排列。LV5+ 的10%成长仍是占位。

怪物深层成长、深层加入或替换技能、人数血量倍率是不同步骤。应在设计表分别列出基础值、层数成长后值和各人数下的最终血量；防御不随目前的深层血量/攻击公式自动成长。

深层技能变化的入口是基础战斗编成的 `DepthProgressionCode`，它关联 `MonsterCombat.DepthProgressions`。下面是合并到 `MonsterCombat` 的配置示意，使用已存在的技能与替换编成代码；`design-example` 仅为示例名称，尚未接入任何副本：

```json
{
  "Profiles": {
    "design-example": {
      "SkillUseChancePercent": 60,
      "Skills": [{ "Code": "goldtooth-smash", "Weight": 1 }],
      "DepthProgressionCode": "design-example-depth"
    }
  },
  "DepthProgressions": {
    "design-example-depth": [
      { "Depth": 4, "AddedSkills": [{ "Code": "goldtooth-roar", "Weight": 1 }] },
      { "Depth": 10, "ReplacementProfileCode": "goldtooth-endgame" }
    ]
  }
}
```

各阶段按 `Depth` 从低到高累计应用：`AddedSkills` 加入当前编成，`ReplacementProfileCode` 将当前编成替换为指定编成，然后再应用该阶段的新增技能；替换也会替换施放概率。示例在 LV4～9 增加咆哮，LV10 起采用替换编成。累计阶段中重复技能会被配置校验拒绝。要启用此变化，编成中的怪物应设置 `IsBoss=true`、`CombatProfileCode=design-example`，副本的 `MaximumDepth` 应至少覆盖所需层数；此处是按挑战层数选择编成，不是战斗中切换 Boss 阶段。

## 房间与挑战生命周期

[DungeonRunRulesService](../Game.Server/Services/DungeonRunRulesService.cs) 为一间房保存一份独立规则快照，并以序列化内容的校验值标识 `Revision`。快照不放进每次房间轮询响应，也不会在每次重复挑战时从当前配置重新生成。

冻结范围是副本侧：怪物基础属性与编成、怪物技能及状态定义、基础掉落表、稀有种子概率、精通与挑战定义、人数倍率、奖励资格，以及副本类型分支。一个房间的所有 `RunSequence` 使用同一份规则快照。部署调参之后，**新建房间使用新配置，已有房间手动重置或自动重开仍使用原快照**。

玩家技能、职业常量、装备模板升级、经验与等级策略仍遵循全局既有规则。奖励中的装备在落包时仍会执行现有模板迁移策略；不能把副本快照理解成整个游戏跨版本完全回放。规则快照也不冻结随机数流。

尚无完整快照的旧房间会保留已有怪物实体与已有深层定义，再捕获缺失的副本侧配置。旧房间无法恢复升级前未曾保存的技能或奖励配置，因此其首次捕获属于兼容补全，不是历史规则重建。启动补全和运行中的首次捕获均需由调用方保存；规则服务本身不隐式提交数据库。

[DungeonRunLifecycleService.BeginNextRunAsync](../Game.Server/Services/DungeonRunLifecycleService.cs) 是手动重置和自动重开的共同入口：

1. 清除运行中的怪物状态、意图和临时战斗加成，恢复角色生命。
2. 重置技能与消耗品冷却、药水操作状态、临时增益和本回合队列；清除本次参与标志，保留玩家永久自动设置。
3. 将回合号归零，推进 `RunSequence`，用原房间快照恢复已有怪物，不重新创建编成实体。
4. 重设准备或重开等待时间，再按当前队伍人数同步血量倍率和首名怪物意图。
5. 调用方增加房间版本并保存。此前挑战的奖励、参与者精通和治疗药水额度历史保留，各自通过挑战序号隔离。

每回合清理只移除确认与动作队列，不能清掉整次挑战的参与记录。波次推进继续使用同一挑战序号。失败结算保留既有已获得奖励语义；重开不撤销或重新发放前次奖励。

关闭房间与重开不是同一种操作。关闭终结房间活动并保留现有记录；解散房间会删除其规则快照。当前未实现统一战绩归档，不能把这些记录承诺为永久战绩。关闭后不再继续心跳推进战斗或接受新战斗动作。详情和奖励读取应按各自接口的关闭房间语义处理。

## 奖励资格与参与者快照

`DungeonRewardEligibility` 有两种策略：

| 策略 | 击杀和通关基础奖励资格 |
| --- | --- |
| `CurrentSlots` | 结算时传入的当前队伍成员，保持普通副本既有行为 |
| `ActualParticipants` | 击杀按实际参与当前怪物的人；通关按实际参与本次挑战的人 |

未显式配置时，普通房间默认 `CurrentSlots`，有深层定义的房间默认 `ActualParticipants`。策略写入房间快照，改变配置不会改变已有房间的资格。

使用完整规则服务并选择 `ActualParticipants` 时，击杀与整次挑战的参与者证据都必须传入；遗漏其中一项会在发奖前返回 `MissingParticipationEvidence`。空集合表示无人符合资格，不能与缺失证据混为一谈。无完整规则服务的旧调用保留兼容行为。

基础奖励资格与实际贡献记录是两个概念。即使配置为 `CurrentSlots`，通关角色进度、战斗里程碑和既有稀有机会仍按实际参与条件计算。角色、副本、挑战序号构成的参与记录保存当次精通；不能在结算时重读刚提高的精通后给本次额外奖励。

新奖励机制应先说明：按怪物还是按整次挑战结算、资格使用哪一组参与者、是否首次通关、是否受精通影响，以及失败时是否保留。重复发放防护继续使用房间、挑战序号、事件键，避免在展示接口中发奖励。

## 直接伤害波动

`CombatDamage.VariancePercent` 当前配置为 `3`，表示角色与怪物的直接伤害采用 ±3% 的随机系数。先按原公式处理技能倍率、防御、暴击、属性、增减伤、职业倍率及易伤等，得到原本的整数伤害，再乘以均匀分布的 `0.97～1.03` 系数，完成整数取整后扣除生命。事件、战报和实际扣血使用同一波动结果，生命扣除仍受目标剩余生命限制。

整数伤害采用概率取整：例如计算出 `9.7`，有 70% 概率取 10、30% 概率取 9。这样基础 10 点伤害大多数时候仍为 10，偶尔出现 9 或 11；基础 100 点伤害落在 97～103。整数精度可能使小额伤害的单次相对变化超过 3%，但除触及最小 1 点或整数上限的情况外，不因取整系统性降低或提高平均伤害。没有额外设置“必定与上次不同”，连续出现相同数值仍是正常结果。

每个直接命中的目标与伤害段独立抽取。普通攻击、技能、魂印主击、反击和按独立攻击倍率计算的追加攻击都经过同一入口；按已结算主击伤害计算的普攻追击、魂印追加及斩杀派生效果不再重复施加波动。治疗、护盾、持续伤害不单独随机，原本按伤害计算的吸血等效果仍自然跟随主击。

该参数写入房间快照的 `DirectDamageVariancePercent`。新建房间采用新配置；旧 JSON 缺少此字段时为 0，已有房间与重开不会被突然改变。参数为 0 时不额外消耗随机数，保留无波动基线；配置支持 0～100，当前默认配置值为 3。

伤害算法复用战斗传入的随机数实例。模拟器在相同配置、种子与控制策略下可复现完整轨迹；启用波动会消耗新的随机数，因此新旧配置之间的暴击、技能选择或掉落轨迹也可能随随机序列推进而不同。原有无波动固定轨迹保留，并单独验证启用 3% 的配置；这不承诺服务器跨进程恢复随机数流。

## 多账号组队掉率加成

`Rewards.CoopDropBonus` 控制基础随机道具掉率，当前测试档位为 `PercentPerAdditionalUser=10`、`MaximumPercent=40`。它按账号去重，不按角色或槽位计数：

| 本次奖励事件实际参战账号数 | 相对掉率加成 | 基础 10% 的道具掉率 |
| --- | --- | --- |
| 1 | 0% | 10% |
| 2 | 10% | 11% |
| 3 | 20% | 12% |
| 4 | 30% | 13% |
| 5 | 40% | 14% |

最终概率为 `min(100%, 基础概率 × (1 + 加成百分比 / 100))`。0% 仍不掉落，100% 仍按原数量必掉，不因溢出概率额外增加数量。一个账号出五个角色时没有组队加成；同一账号的多个实际参战角色可以分别获得所在队伍的加成。

击杀采用实际参加该怪物战斗的角色，通关采用实际参加本次挑战的角色，并与当前可获基础奖励的角色集合取交集后统计账号。死亡但已参战的角色仍有效；空槽、错误账号归属、未参战角色不计入加成，也不享受加成。成员离队后不会保留一个虚假的额外账号名额，轮换账号不累计超过当前队伍。缺少参战证据时不推测组队加成，既有基础奖励资格仍遵循原策略。

加成适用于普通击杀与通关基础表中的武器、消耗品、材料和魂印随机掉落。金币、经验、首次通关整表、新手保底、精通额外抽取、挑战碎片及独立稀有种子渠道保持原规则。因此满精通时的整体收益增幅不应直接表述为全部奖励增加 40%。

规则参数进入房间规则快照，新建房间使用新参数；旧快照缺少此字段时按零加成处理，重开仍保留旧规则。实际账号数和加成随每个奖励事件保存，重试不会重复抽取或按新阵容重算已经产生的奖励。组队阵容可以随原有规则变化，房间快照冻结的是加成参数，而非账号名单。

房间展示的是当前阵容的预计加成，最终按上述参战条件结算。全队自动战斗与手动战斗使用同一规则；无需按伤害排名，治疗和辅助角色只要实际参战也能计入。

该功能识别不同账号，不能据此证明账号背后是不同真人。现有奖励仍按角色独立获取，增加每角色掉率不等于补足减少出战角色带来的账号总收益损失。数值评估必须同时比较角色、账号和队伍总产出；如果后续目标是让“单角色跨玩家组队”也超过“单账号五角色”的账号收益，应另行设计账号收益预算，不能直接把加成调高并假定达成了目标。

## 下一轮机制设计需要先确定的规则

当前模型适合设计“队伍对单名活动敌人”的技能轮转和多波压力。若要同时存在多个可选择敌人，应先扩展目标身份与存活敌人集合，再处理前端选择、意图、伤害、状态、奖励事件和轨迹格式；只在编成里增加怪物不会获得同时战斗能力。

破甲、侵蚀、冻结、反射等名称应先写成可验证的规则，再选择复用已有效果或新增类型。已有魂印伤害及减防、追加伤害、打断等能力不自动等价于新设计的同名机制。至少确认：

- 触发时点与结算顺序：行动前、命中后、回合末，还是下一次行动；死亡后是否继续。
- 数值基准与取整：攻击、目标最大生命、实际扣血或计算伤害；属性相克、防御、暴击、增减伤的顺序。
- 叠层与消耗：上限、刷新方式、跨波或跨挑战保留、驱散、抵抗和解除条件。
- 反射与追加伤害：是否再次触发反射、吸血、反击、状态和奖励；必须有防递归规则。
- 冻结与打断：取消已公布意图还是跳过行动，冷却是否推进，对首领是否特殊。

新增执行规则应进入战斗效果或状态执行边界，沿用结构化事件。房间服务负责入口、权限和展示，挑战服务负责推进与结算，不应各自新增另一套伤害或奖励公式。

## 模拟与验证入口

[tools/Game.BalanceSimulator](../tools/Game.BalanceSimulator/README.md) 使用隔离的内存 SQLite 和生产战斗服务。可用 `--config` 测试候选配置，按角色、元素、装备阶段、队伍人数、目标和随机种子采样；`--trace` 输出逐回合事实和指纹，定位首次行为差异。完整选项以工具说明和参数校验为准。

```powershell
dotnet run --project tools/Game.BalanceSimulator -- --dungeon-code kobold-mine-depths --depth 4 --mastery 2 --starting-potions 5 --stages raid --roles knight --runs 5 --seed-start 7213 --trace --output depth-four.json
```

`--dungeon-code` 直接选世界目录中的副本，不与 `--targets` 同时使用；普通 `kobold-mine` 只支持 `--depth 1`，深层 `kobold-mine-depths` 按配置最大层数校验。`--mastery` 指定每名角色本次挑战初始精通（0～4），不是宣称真实角色已有该通关历史；模拟器另行准备入场与自动资格。`--starting-potions` 指定每人初始小型治疗药水库存，实际使用仍受生产规则中的额度与自动条件约束。不同库存应分别采样，避免无限药水掩盖消耗压力。

设计比较应固定配置、种子、装备、技能与控制策略，并列出胜率、回合数、生命压力和奖励收益的目标范围。固定种子轨迹用于检查行为变化，多种子采样用于评估数值波动；两者不能互相替代。重新创建服务时也应保留同一随机数实例与已消耗的随机状态。

下一轮具体设计建议先选一个副本，给出每波基础属性、队伍规模、技能轮转、状态规则、目标战斗时长、失败压力和奖励预算，再决定哪些仅需配置、哪些需要执行规则扩展。
